# Один интерфейс — два исполнения: проверка Compose ↔ DOM

Цель: Compose-версия (`:app`, web — Compose wasm на Skia) и DOM-версия (`:webhtml`, Compose runtime + DOM) дают
один и тот же экран — те же размеры, отступы, цвета, состав элементов и анимации. Расхождение ловит скрипт, а не глаз.

Ветка: `web/compose-html`. Коммиты — по-русски, коротко, по этапу на коммит.

## Как устроено сейчас

- `:webhtml` берёт `app/src/commonMain` целиком, кроме файлов UI (`appUiFiles` в `webhtml/build.gradle.kts`):
  ViewModel, состояние (`ViewerUiState`), разбор файлов — общие. Экраны написаны дважды:
  `app/.../ViewerScreen.kt` и др. (Compose UI) и `webhtml/.../web/*.kt` + `kotin.css` (DOM).
- Цвета: `KotinColors` в `Theme.kt` (Compose `Color`, в webhtml не попадает) и вручную — `:root` в `kotin.css`.
- Размеры (`EDGE`, `SELECTION_WIDTH`, `sizes.*`, радиусы, `MOTION_MS`) объявлены по разу в каждой версии.

## Этап 1. Токены из одного места

1. Новый файл `app/src/commonMain/kotlin/dev/iskandern/kotin/DesignTokens.kt` без Compose UI: цвета — `Long` ARGB,
   размеры — `Int` (dp = px CSS), длительности и кривые (кубические Безье числами), параметры мягкой тени.
   Не в списке `appUiFiles` — попадает в обе сборки.
2. `Theme.kt` (`KotinColors`) и константы размеров в app берут значения оттуда. Поведение app не меняется ни на пиксель.
3. webhtml при старте (до первой композиции) выставляет CSS-переменные `:root` из `DesignTokens`; из `kotin.css`
   уходят захардкоженные цвета (остаются `var(--…)`). Константы размеров в webhtml — тоже из `DesignTokens`.
4. Проверка: `./gradlew :app:jvmTest :webhtml:wasmJsBrowserDistribution :app:wasmJsBrowserDistribution`,
   глазами — обе сборки до и после выглядят так же.

## Этап 2. Истории — фиксированные состояния экрана

1. `app/src/commonMain/.../Stories.kt`: список историй — имя и как получить состояние. Состояние строится через
   обычный `ViewerViewModel` (открыть файл, выбрать объект, раскрыть, открыть меню), а не подделкой полей: тогда
   история — тот же путь, что у пользователя. Объект выбирать по номеру/id, без долгого нажатия в сцене
   (при необходимости — небольшой метод выбора по id во ViewModel).
2. Файлы историй — синтетические и маленькие, кладутся в ресурсы обеих web-сборок (как демо-файлы) — например,
   сгенерированные `scripts/gen_test_landxml.py`: трасса с пикетами, поверхность из нескольких треугольников,
   несколько объектов в одной точке (кандидаты).
3. Обе web-сборки понимают `?story=<имя>`; `&scene=0` — без Filament (ровный фон `--scene`), чтобы история
   открывалась за секунды и одинаково в обеих. Размер окна задаёт сам Playwright.
4. Первый набор (десктоп 1200×800 и телефон 390×844):
   - `empty` — пустой экран; `loaded` — файл открыт, карточка файла;
   - `menu` — меню (десктоп: панель; телефон: боковое с затемнением);
   - `card` / `card-expanded` — карточка выбранного, свёрнута и раскрыта;
   - `candidates` / `candidates-list` — переключатель «Рядом ещё объекты» и раскрытый список;
   - `sheet` / `sheet-expanded` — шторка телефона;
   - `hint`, `labels-notice`, `load-error` — плашки и ошибка.
5. Готово, когда каждая история открывается в обеих сборках и выглядит как в жизни.

## Этап 3. Рамки элементов и сравнение

1. Разметка ключевых элементов одним и тем же именем в обеих версиях: карточка файла, ≡, меню, карточка выбора,
   её шапка, крестик, «развернуть», ячейки свойств, переключатель кандидатов, шторка, ручка, кнопки камеры,
   индикатор осей, плашки.
   - Compose: `Modifier.uiTag("selection-card")` в общем UI-коде app; в режиме историй пишет рамку
     (`onGloballyPositioned`, в px CSS) в реестр; вне историй — пустой модификатор, без затрат.
   - DOM: атрибут `data-ui="selection-card"`.
2. Обе сборки отдают `window.kotinLayout()` → `{ имя: {x, y, w, h, visible} }` и `window.kotinIdle()` — анимации
   закончились (без этого снимки ловят середину перехода).
3. Скрипт `scripts/ui-sync/compare.mjs` (Node + Playwright; `package.json` рядом, зависимости — только туда):
   собирает/берёт `app/build/dist/wasmJs/productionExecutable` и `webhtml/build/dist/wasmJs/productionExecutable`,
   поднимает оба на локальном сервере с отключённым кэшем, для каждой истории и размера открывает обе, ждёт
   `kotinIdle`, сравнивает рамки с допуском ±1 px, снимает скриншоты.
4. Отчёт `agent-out/ui-sync/index.html`: по истории — Compose | DOM | разница (pixelmatch, текст маской или с порогом),
   таблица рамок с расхождениями красным. Код выхода ≠ 0, если рамки расходятся сверх допуска.
5. Готово, когда скрипт проходит все истории и честно показывает нынешние расхождения (их не прятать допуском).

## Этап 4. Починить найденные расхождения

По отчёту — править DOM-версию под Compose (эталон — app), по коммиту на расхождение. Если эталон спорный —
записать в отчёт и спросить владельца, а не выбирать самому.

## Этап 5 (позже, с согласия владельца). CI и анимации

- Шаг в `.github/workflows/ci.yml`: после сборок web — `compare.mjs`, отчёт артефактом. Правки workflow — только
  с явного согласия владельца.
- Анимации: покадровая запись рамок при переходах (раскрыть карточку, закрыть меню, натянуть шторку) и сравнение
  длительности и конечного положения.

## Правила

- Эталон — Compose-версия; DOM подгоняется под неё. Обратные правки app — только если они нужны для токенов
  или разметки и не меняют вид.
- Перф и вид app не трогать; общий код (`commonMain`) — без `java.*`.
- Локальные сборки отдавать с отключённым кэшем (иначе браузер показывает старую сборку).
- Не пушить; по завершении этапа — коммит и короткий отчёт со скриншотами из `agent-out/`.
